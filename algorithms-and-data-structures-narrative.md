# Algorithms and Data Structure

## CS-360 Contact Service Enhancement Narrative

For the algorithms and data structures part of my ePortfolio I chose an artifact that I created back in CS 360: Mobile Architecture and Programming called WeighPoint, which is an Android weight tracking application. The application has been developed as a mobile application, where users can register for an account, log weight change on a daily basis, set a desired weight range, view the weight history, and optionally view the SMS notifications. Developed in Java with Android Studio up to the application, with a local SQLite database that keeps user and weight data. 

WeighPoint was chosen because the original application was functional, but would show the weight history data, but not really analyze it. Users could record, edit, and delete weight data, but the program didn't do much with the recorded weight data after it was stored. This was an opportunity to code a feature that could be more useful yet to show off my knowledge of algorithms and data structures. I didn't want to recreate the original application but wanted to expand upon it and make the data meaningful to the user. 

The major improvement was the redesign of the Weight History section of WeighPoint to accommodate organization and analysis of the data. In the initial code, the weight values were grabbed from the SQLite database and presented on the screen. To enhance this, I created a WeightEntry model and wrapped the retrieved database records in a collection of WeightEntry objects. It would enable the application to manipulate the data without depending on the Cursor to the database and also give a structure for carrying out calculations, filtering, and sorting that could be reused. 

I also defined a new class for each of these collections called WeightAnalytics, which holds algorithms for processing the collections. An important design choice was to separate the analytics logic from the Android activity, which reduced the burden of the user interface and enabled analysis algorithms to be tested separately from the user interface. The class now determines minimum, maximum, and average weights, total weight changes, moving averages, and weight trends. It also includes algorithms to filter the records by date and sort the records by date and weight. 

A few of these improvements exhibit particular algorithmic ideas. Sorting does not alter the source data—there are no unexpected changes to the underlying data because of the sort. The complexity of these sorting operations is around O(n log n). Date filtering requires O(n) time because it processes every entry once. This moving-average calculation is applied with a so-called sliding-window approach. The algorithm doesn't recalculate all the values in each window but rather adds the value coming into the window and subtracts the value going out of the window. The time required for the sliding-window calculation is O(n) when the entries are entered in chronological order. 

The moving average is calculated using the weight recorded in the past, in order, and not calendar days. It was important to note this distinction because a user might not be able to record weight every day. When displaying the recent average, up to the 7 most recent entries from the log will be used, so that it can give useful information even if the user does not log every day. 

The improved interface also allows users to manage the processing and presentation of their data. Records of weight may be filtered to All Time, Last 7 Days, Last 30 Days, and Last 90 Days. Records may also be ordered by Newest, Oldest, Lowest Weight, or Highest Weight. The analytics are on the date filter but before the display sort. This means that when the Date Range changes, the analysis changes, but a change in the way that the records are displayed does not change the calculated results. This separation is a key factor in having the feature operate predictably. The enhancement also maintained the existing functionality to add, edit, and delete weight records, so that the additional functionality could be added to an existing application, without removing anything that already worked. 

The main enhancement for this is the third and fourth Computer Science program outcomes that I identified in Module One. The third outcome is concerned with the design and assessment of computing solutions based on algorithmic principles and computer science practices and the consideration of trade-offs of design decisions. The fourth outcome is concerned with the application of sound techniques, skills, and tools to develop computing solutions that deliver value. I feel the enhancement that I completed is still aligned with my original goal of covering the outcomes, and I do not foresee the need to adjust what outcomes I wanted to cover with this artifact. 

The third outcome is most clearly defined in the collection of processing and analytics algorithms. I needed to think about representing weight records, sorting and filtering relationships, calculating moving averages, and finding overall trends. I also took into account the complexity and compromises of these decisions. The analytics to be performed are O(n) in the case of in-memory List<WeightEntry>, and sorting can take O(n log n) time. SQLite might do some of its sorting and filtering in a single database query, and this might be more suitable for a much larger data set. But it is expected that a personal weight-tracking app has a reasonably small number of records. Collections in the application layer are thus a good compromise to maintain reusability and separating algorithms and making them independently testable. 

The fourth outcome is achieved by combining the use of Java collections, SQLite data, components of the Android user interface, and automated unit testing in a functional application. The enhancement did not stop putting standalone algorithms in place. The algorithms were integrated into the current Android app to enable the user to interact with the algorithms through filtering/sorting controls and receive updated analytics instantly. This means that although the information is being gathered, it will be of added value to the information the application was collecting, rather than something it wasn't designed for. 

The most important thing I learned during this enhancement is that it's not just about the addition of new features in an existing application. Before I could get a sense of where I wanted to place the new algorithms, I had to comprehend how the old application was able to retrieve, display and modify its data. The conversion to WeightEntry objects was a sort of "separation of concerns" regarding data storage and data analysis. Having a separate class for analytics also helped to make the application easier to reason and made it easier to test algorithms without relying on the Android interface. 

Testing was particularly crucial during the enhancement. I made some unit tests for the calculations, sorting, filtering, moving averages, classification of trends, null, empty collections, and other edge cases. An interesting challenge was when we were testing the date-range filter, where one of the comments was that it was helpful to run tests that would exclude the filter. The application stored weight dates as calendar dates and also had a time of day in the reference date used to filter the date. This caused a problem when there was an entry exactly on the start date boundary of a date range, which may have been mistakenly omitted as it was thought to be midnight. 

I decided not to immediately change the algorithm, but instead I wrote a regression test that reproduces the problem. At that time, 21 out of 22 tests were good, and the new boundary test failed as it should have. Next, I added the ability to normalize the reference date to midnight, before computing the start of the range. After making the correction, all 22-unit tests passed. This was a reminder that tests cannot just be used to check code works but to establish a problem before trying to fix it. 

I also conducted manual testing of the Android application that was developed to check its behavior when deployed into the real user interface with the algorithms. I've tried filtering by 7, 30, 90 and all-time days as well as sorting by newest first, oldest first, lowest weight and highest weight. I found that by changing the sort of display, the calculations did not change the incorrect way, and that by changing the date range, they were correctly recalculating. Lastly, I performed tests on the existing add, edit, and delete feature to make sure that the feature has not caused any regressions in the application. 

Overall, this is a step up from the way I approached software development when I created WeighPoint initially. The initial application focused mainly on getting the functions required to work. I did more thought in this enhancement about separation of responsibility, re-usable data structure, efficiency of the algorithm, edge cases, regression tests and the impact that a change may have on existing functionality. While this improvement was good in many ways, the most valuable part of it was that it wasn't a single calculation or sorting option or interface change. It was learning to carefully treat the application as an existing software system in need of improvement rather than as code that can just be rewritten if a new requirement arises.
