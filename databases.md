# Databases

## CS-340 Grazioso Salvare Dashboard Enhancement Narrative

For the database category, I chose the Grazioso Salvare Animal Shelter dashboard which I created in CS 340: Client/Server Development. The project is built with Python, MongoDB, PyMongo, Dash, Plotly and Dash Leaflet. It was designed to offer an interactive application to view animal shelter data and view animals that would qualify for the rescue training criteria. The original application featured a re-usable CRUD module for interacting with MongoDB as well as a dashboard which gave a user the ability to filter shelter records, show the information of each shelter's animal, and display the location of the animals the user selected on a map. This artifact was chosen because it gave me a good base to show how to develop a database, and it allowed me to work on multiple methods of data retrieval, validation, processing, and protection within the application. 

I felt this artifact was a good match for my ePortfolio because although I proved I could write an app to a database and do basic CRUD operations, I did not prove many of the database optimization and data-management techniques I have learned since taking CS 340. A major drawback of the initial design was that the dashboard was able to get full results from MongoDB and then do further processing in Python. This has worked for the given data set, but it would become more inefficient as more data was stored. I've re-designed parts of the data-access layer to have more of that done by mongo. 

One of the major improvements was the addition of server-side pagination and sorting. The improved application fetches only the records needed for the current page displayed on the dashboard instead of the whole collection. I added a paginated read function using sorting, skip(), limit() operations and a count operation to find out how many pages there are results. I then added these features to the Dash interface and made sure that when I switch to another page or sort a column in the database, I get the right query to the database. This improvement enabled me to see that efficiency in the database goes beyond simply getting the right answers. The amount of information exchanged and processed is also important. What helps in a small database can become a problem as the database grows, so avoiding unnecessary retrieval is an important consideration when designing a scalable application. 

I also introduced some aggregation logic in MongoDB to take the calculations closer to the data. The original dashboard used pandas to calculate the Breed based on the already retrieved data, which could be done with python as well. The improved version takes advantage of an aggregation pipeline with $match, $group, $sort, and $limit to determine the most common breeds for the current rescue criteria for the database. This will create a summary and then upload it to the dashboard for visualization. This was a significant enhancement as it revealed my understanding of the role of the database. Instead of just sourcing the data from MongoDB for Python to read and act upon, I could rely on MongoDB as part of the analytical solution of the application. 

Another important area of improvements was the creation of indexes and optimizing queries in the database. I have built an index on animal_id and a compound index on fields that are routinely used in filters on the app for rescuing animals such as animal_type, breed, sex_upon_outcome and age_upon_outcome_in_weeks. After that, I analyzed the use of those indexes and their performance using MongoDB query plans and execution stats. This was one of the best and most useful aspects of the enhancement as it was possible to get tangible evidence of the impact of a design decision for the database. During testing, the indexed rescue query returned 17 matching records while examining only 17 documents and 22 index keys. For the sake of comparison, I did a collection scan on MongoDB, and the same query returned results of 17 records, but scanned through all 10,000 documents in the collection. This was a reduction of about 99.83% of the documents which were examined. The number of documents examined was more significant than milliseconds as the database was running locally, hence different times of execution between tests. 

In the process, I also learned that optimization comes with compromises. Many indexes could be formed for various fields, but indexes take up extra disk space and impact insertion and updates of records. Rather, I chose indexes that matched the queries that the application really makes. In the same way, the pagination that's implemented in this project using skip() and limit() makes sense for the (relatively) small number of records (~10,000) in this project, but for a large-scale production database, it may be a better idea to use a cursor or range-based approach to pagination. The decision-making process guided me in my progression towards the Course Outcome of designing and evaluating computing solutions, taking into account the considerations of trade-offs associated with technical decisions. 

Another thing I wanted to enhance was data integrity. I added normalization, so that any leading or trailing whitespace that may have been entered in an important text field is stripped away before information is stored. I also added validation for required animal fields and numerical age values. The checks are now part of the create and update operations and are no longer separate from utility functions. Valid records were determined and were able to be normalized and stored with the correct data, while records that lacked required information, contained blank required values, and those that contained negative ages were rejected. This work underscores the need to preserve data quality at the point of information entry, rather than if all callers will enter information in a correct format. 

Security was also taken into account for enhancement. When developing, I recognized that it was not necessary to include a database password in the source code, and that it was a potential security risk, especially if my project was uploaded to a public source code repository as part of my portfolio. I updated the application and the test code to get the MongoDB password from an environment variable instead. This application now terminates with an appropriate error when the password is not available, as opposed to embedding it into the application. The MongoDB connection remains an authenticated connection. This is not a huge change compared to the database optimization work but helps reinforce a mindset for security around how the architecture of the application could expose data or credentials even if it is doing its intended work. 

The enhancement achieved course outcomes that I originally planned for, including designing and evaluating computing solutions, use of appropriate computing techniques and tools, and a security mindset. The project now shows more than just basic database connectivity and CRUD. It shows how to handle credentials securely, how to normalize and validate data, how to analyze the query plan and execution statistics both on the server and from the database, how to use indexing, and how to use server-side pagination and sorting. I also kept the original read(), and added the improved paginated operations. This enabled the application to be enhanced with new functionality without breaking its user interface, which was provided by the original artifact. At the moment, I don't believe I need to modify my intended outcomes to cover as the enhancements which have been completed show evidence of the intended outcomes. 

One of the issues that I had was that whenever I made an enhancement in one area, it caused some unexpected behavior in other areas of the application. Changing the Dash table to implement some custom server-side pagination caused the behavior of filtering and page state to change. The paging functionalities were not suitable for the new approach, which is done natively in the filter, so I kept the "rescue" style of filtering and moved it to the filter hosted by MongoDB. I also found that if I swapped between different rescue filters and then viewed a later page number, I would be left on that same page number. Although the database query was correct, the behavior was confusing from a user's perspective. To correct this, I detected when the rescue filter changed and reset the table to the first page. This was a reminder to me that an enhancement can't be judged by the new database method alone. The impact of changes in the data layer is felt at the interface level and in the overall UX. 

Testing therefore was an important aspect of the enhancement process. Designed and refactored a database enhancement test script to test the connection, pagination and sorting, aggregation, index creation, query plans, indexed versus non-indexed performance, normalization, validation, record creation and updates. Temporary records are generated during testing and then deleted after the test has been completed to ensure that the testing process doesn't affect the shelter data set permanently. I also did a manual test of the dashboard to ensure that filtering, paging, sorting, visualizations, and mapping still functioned following the changes to the database. This was a combination of both codebase testing and application regression testing that gave me increased confidence that the enhancement did not harm the artifact's original function. 

Overall, this is a great improvement in my thinking about the development of the database. When I originally completed CS 340, much of my focus was on successfully connecting Python to MongoDB and making CRUD operations work. The main criterion for success was the return of the correct records. This enhancement gave me an appreciation that a query does more than run smoothly, it examines zero, one, or many records, pulls out a great deal of data from an application, performs analytical processing, ensures consistency of stored information, and secures database credentials. The updated Grazioso Salvare application is thus an improvement to the original art and a more evident example of the skills in designing and creating a database that I have acquired throughout the Computer Science program.
