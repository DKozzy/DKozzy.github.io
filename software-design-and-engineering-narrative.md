# Software Engineering and Design

## CS-320 Contact Service Enhancement Narrative

As my software design and engineering artifact, I chose the Contact Service application that I created in CS-320: Software Testing, Automation, and Quality Assurance. The original project was coded in Java and planned to work with a class called Contact and a class called ContactService for managing the Contact information. Contacts include an ID, first name, last name, phone number, and address. The service had limited functionality: adding, removing and updating contacts, and JUnit tests were applied to ensure that the application adhered to the validation rules. I chose this artifact because I felt it was a good base to showcase how a rather simple application can be remodeled and extended with the software engineering skills I have acquired during the computer science program. 

The original artifact was able to address the requirements of CS-320, but it was not very functional. The application was mainly an example of object-oriented programming and automated testing but not a fully-fledged contact management system. Contact details were available only during the time the program was operating; there were no interfaces to interact with the program, and the users were unable to search, sort, import, or export their information. There was also a need to validate the implementation throughout the system as the application expanded, making it more difficult to keep the rules consistent. Because of these restrictions, I had a few moments to enhance the functionality as well as the design of the application. 

One of my first improvements was to enhance and focus on contact validation. The improved Contact class now includes validation procedures for creating a contact, as well as for updating contact details. Contact IDs, names and addresses cannot be null or blank and must be limited to a specific length of characters. Phone numbers must be 10 digits in length. These rules were centralized, eliminating duplicated validation code and making sure that the same rules are applied no matter how the contact information is added to the application. I also made the contact ID immutable after creation as it is the ID which uniquely identifies the contact. These changes have also brought a level of maintainability and minimized the chance of invalid data being entered into the system. 

I made a major extension to the ContactService class to support a more comprehensive application. The service also now allows contacts to be added, deleted, and updated, as well as retrieved by ID, displayed as a list of contacts, sorted by first or last name, and searched by partial and case-insensitive contact names. Duplicate contact IDs and phone numbers are rejected to help preserve data integrity. I also preserved the old individual update methods but added the functionality to update a whole contact. During development, keeping those existing methods was important because they were in use when the existing tests that relied on these methods started failing. The methods emphasized the value of maintaining backward compatibility when improving a well-established software system, as opposed to developing a new system from the ground up. 

One of the other big improvements was the ability to store data permanently. The original was just a memory contact application, and all information would be lost when the program was closed. I developed a ContactStorage class that stores and retrieves Contact data in CSV files. Dividing the responsibility for storing the data from the service layer helped to clarify the architecture and give each class a more single-minded purpose. When the application is launched, it now loads all contacts previously saved, and it can save changes for later use. This turned the artifact into an application that can store information between executions of contact operations. 

The ability to store was enhanced with CSV import/export. These features need to be more than just being able to identify where each field ends, since valid contact data can have commas or quotation marks, especially addresses. Added CSV escaping and parsing support for fields and escaped quotation marks. In testing, I also found that a CSV file with a row of comma separators in Microsoft Excel was considered visually empty. The original importer tried to send it as a contact and refused the file. I made some changes to the importer to detect rows that have no data in any of the cells and safely skip them. A regression test was then added to make sure that it wouldn't come back in future change. It was a good example of how software could perform well with specific test data and must be treated differently when used with real data and real tools. 

I created a menu driven command line interface so that it would actually be usable without having to explicitly call Java methods and functions. The interface allows users to add, view, search, update, delete, and sort contacts. Users can also store their data and import/export CSV files. The interface does not contain business logic; it delegates the contact operations to ContactService. This is to ensure that the application presentation, business logic, and storage responsibilities are better separated. This therefore allows for the ability to replace or expand individual components without affecting other unrelated parts of the system. 

I added persistent activity logging to make it more traceable and aware of errors. Errors and informational events are logged in the ActivityLogger with a time stamp, in a separate log file. Actions like adding, updating, deletion, importing, exporting, and saving contacts can then be reviewed when the application has been terminated. If logging fails, it is done in such a way that it does not affect the success of the contact operation. This meant I needed to think about how to use logging as a supporting feature and not something that is unnecessary and might interpose itself in the application's primary function. 

Security and data integrity were taken into consideration during the enhancement. The application is not sensitive to authentication or financial information, but it does show a security-minded design of the software. User data, and imported data is validated before it is accepted, malformed CSV data is rejected, duplicate identifiers and phone numbers are not allowed, and exceptions are handled rather than silently accepted. Import operations are also checked before adding new contacts to the active collection, so that an import that is not completely valid does not leave data in an inconsistent state in the application. The decisions illustrate how to apply security as part of the software design process and not as an afterthought. 

The artifact was important as a testing artifact, given that it was part of a software testing course. I used more than just manual testing and added new functionality to the JUnit test suites. The new tests include contact creation, field validation, boundary values, setters, searching, sorting, duplicate detection, persistent storage, CSV import/export, malformed data, empty CSV rows, and activity logging. Temporary directories are used for file-based tests to avoid overwriting the real information stored in the application by automated testing. Integration tests also validate the interaction between different components, such as saving contacts from one service instance and loading them from a different service instance, simulating a restart of the application. This unit and integration testing approach helped me have confidence that the enhancements wouldn't affect existing functionality. 

This enhancement is applied to illustrate a number of the outcomes of the CS-499 course. When redesigning a small application into a more comprehensive layered system, I applied software engineering techniques and assessed maintainability and compatibility with existing functionality. The search, sort, duplicate detection, CSV parsing and validation capabilities called for logical problem solving and manipulation of various data situations. Persistent storage, importing and exporting, logging and command-line interface illustrate my use of suitable computing techniques and tools to achieve a working solution. The enhanced validation, error handling, data integrity, and logging features also show a commitment to security by looking ahead at how invalid and unexpected data might impact the system. 

The process of completing this enhancement gave me insight into the way my software development process has evolved since I made the artifact. The main concern in CS-320 was making sure that the classes were performing as they should be and that my tests showed the classes were doing that. This capstone enhancement required me to think outside the box, literally, about whether or not an individual technique was effective. I thought about how each component of the app should communicate with one another, how to store information between runs, how to make sure that there were no unexpected data coming from outside of the file because the app was dependent on that data, how to ensure that existing functionality would still be available when the app changed and how future developers would be able to understand what the application does with code and documentation. The resulting product is thus more than the original assignment as it is expanded. It reflects how I have matured from designing individual requirements to the design, development, and maintenance of a comprehensive software solution.
